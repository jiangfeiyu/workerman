【Linux 核心哲学】为什么 Unix/Linux 坚持“一切皆文件（Everything is a file）”？什么是文件描述符（FD）？	<b>1. 统一接口</b>：<br>避免针对键盘、屏幕、磁盘、网卡套接字各搞一套繁琐读写 API。Linux 将所有 I/O 抽象为流，统一使用 <code>read/write/close</code> 操作；<br><br><b>2. FD 的本质</b>：<br>内核为每个进程维护的“打开文件表”的<b>整数下标索引（从 0 开始排队的非负整数）</b>；<br><br><b>3. 生活比喻</b>：<br>就像在银行办业务时领到的排队挂号小纸条，手握号码牌就能操作对应资源。	Linux哲学 一切皆文件 FD 文件描述符 Chapter02
【Linux 基础内功】任何 Linux 进程一出生（即使代码是空的），内核就默认在它肚子里插好了哪 3 根管子（3 个 FD）？它们默认分别指向哪里？	• <b><code>FD 0 (STDIN)</code> 标准输入</b>：默认连接在<b>键盘</b>（用来吸取用户输入）；<br>• <b><code>FD 1 (STDOUT)</code> 标准输出</b>：默认连接在<b>终端屏幕</b>（用于打印普通业务日志与 echo 输出）；<br>• <b><code>FD 2 (STDERR)</code> 标准错误</b>：默认<b>同样连接在终端屏幕</b>（用于打印警告和致命错误报错）。	Linux基础 STDIN STDOUT STDERR FD012 Chapter02
【Linux 架构设计】既然 1 号管子（STDOUT）已经指向终端屏幕，为什么 Linux 还要多此一举插一根 2 号管子（STDERR）到同一个屏幕上？	<b>1. 核心目的</b>：<br><b>实现“正常业务数据流”与“异常报警流”的彻底解耦与隔离</b>；<br><br><b>2. 重定向场景（关键威力）</b>：<br>当执行 <code>php export.php > bill.txt</code> 导出账单时，重定向符号 <code>></code> 默认<b>只把 1 号管子拔下接到文本文件</b>；<br><br><b>3. 价值</b>：<br>一旦脚本中途发生数据库连接慢等 Warning，2 号管子输出的报错依然直接弹在屏幕上提醒管理员，而绝不会混入并污染导出的 <code>bill.txt</code> 账单数据！	Linux架构 重定向 STDERR 管道隔离 Chapter02
【Linux 内核分配机制】进程打开文件或网络 Socket 时，Linux 内核分配 FD 号码牌遵循什么铁律？（最小可用 FD 原则）	<b>1. 铁律名称</b>：<br><b>【最小可用编号原则（Lowest Available FD）】</b>；<br><br><b>2. 分配行为</b>：<br>内核从 0 开始扫描进程的 FD 表，<b>一旦发现某个槽位处于空闲状态，立刻将这个最小的空位号码发给新打开的资源</b>；<br><br><b>3. 实例验证</b>：<br>若进程已占用 0,1,2,3,4 号；调用 <code>fclose(3)</code> 关掉 3 号后，紧接着下一行 <code>fopen(&quot;c.txt&quot;)</code>，内核必定将刚刚空出的 <b>3 号</b> 分配给 <code>c.txt</code>，绝不会分配 5 号！	Linux内核 FD分配 抢座规则 Chapter02
【PHP 踩坑认知】在 PHP 中对一个文件流句柄强制转为整数 <code>(int)$fp</code> 打印出的数字，与在 <code>/proc/$PID/fd</code> 中看到的内核真实 FD 是一回事吗？	<b>不是一回事！</b><br><br>• <b><code>(int)$fp</code></b>：是 PHP 虚拟机（Zend 引擎）内部为该 Resource 资源变量分配的<b>自增流水号 ID</b>，即使旧文件关闭后新打开文件，这个 ID 也会一直单调递增；<br><br>• <b>内核真实 FD</b>：必须通过 <code>/proc/$PID/fd</code> 或专用系统调用查看，它严格遵循内核的“退座抢座与最小空位复用”机制。	PHP底层 资源句柄 ResourceID 内核FD Chapter02
【生产环境事故】常驻进程若开启守护进程（Daemon）在后台运行，当管理员断开 SSH 黑窗口后，为什么代码里的 <code>echo</code> 会引发诡异异常？	<b>1. 断开危机</b>：<br>SSH 终端关闭后，原先 <code>0, 1, 2</code> 号 FD 所绑定的虚拟终端设备文件（如 <code>/dev/pts/0</code>）直接被操作系统注销销毁；<br><br><b>2. 写入失败</b>：<br>此时代码若执行 <code>echo</code>，底层 <code>write(1, ...)</code> 会因目标设备已不存在而报错（<code>EBADF</code> 或 <code>EIO</code>），甚至可能触发 <code>SIGPIPE</code> 信号导致后台进程瞬间非正常死亡！	守护进程 Daemon SIGPIPE 标准输出异常 Chapter02
【Workerman 源码精读】Workerman 在 <code>Worker::resetStd()</code> 中是如何只用 <code>fclose</code> 和 <code>fopen</code>，就让全项目后续所有 <code>echo</code> 自动静默流进日志文件的？	<b>1. 巧妙步骤</b>：<br>• 先调用 <code>@fclose(STDOUT); @fclose(STDERR);</code> 关闭 1 号和 2 号管子，腾出 1 和 2 号空位；<br>• 紧接着执行 <code>$stdOutStream = fopen(static::$stdoutFile, 'a');</code>；<br><br><b>2. 内核抢座原理</b>：<br>依据“最小可用 FD 原则”，新打开的日志文件被内核精准分配到刚空出来的 <b>1 号槽位（FD 1）</b>！<br><br><b>3. 最终结果</b>：<br>PHP 底层的 <code>echo</code> 是个死脑筋，依然习惯性地往 1 号写，但此时 1 号已偷天换日指向了日志文件，从而神不知鬼不觉地完成了重定向！	Workerman源码 resetStd 重定向 黑魔法 Chapter02
【PHP 垃圾回收 GC 陷阱】在 Workerman 的 <code>resetStd()</code> 中，为什么 <code>fopen</code> 返回的句柄必须存入 <code>static::$outputStream</code> 静态属性，而不能用普通局部变量？	<b>1. 致命陷阱</b>：<br><b>PHP 引用计数垃圾回收机制（GC）</b>！<br><br><b>2. 局部变量的灾难</b>：<br>如果只用局部变量 <code>$stdOutStream</code> 接收，当 <code>resetStd()</code> 函数执行完毕退出时，局部变量引用计数归零被 GC 销毁，PHP 会自动触发析构调用 <code>fclose</code> 将刚刚抢到的 1 号管子又给关了！<br><br><b>3. 破解之道</b>：<br>赋值给类的常驻静态属性 <code>static::$outputStream</code>，保持全局强引用，死死攥住 1 号管子不让 GC 回收。	PHP核心 垃圾回收 GC 引用计数 Workerman源码 Chapter02
【高并发排障】什么是文件描述符泄漏（FD Leak）？会导致什么报错？在高并发网络服务器中通常是由什么代码引起的？	<b>1. 本质定义</b>：<br>打开了文件、Socket 连接或管道后，未能及时执行 <code>fclose/stream_socket_shutdown</code> 关闭释放，导致进程占用的 FD 数量只增不减；<br><br><b>2. 致命报错</b>：<br>当占满单进程上限时，系统调用抛出 <b><code>Too many open files</code></b>，服务器瘫痪无法再接受任何新连接；<br><br><b>3. 常见诱因</b>：<br>连接在异常分支提前 return 未执行 close、或者连接对象被全局数组引用导致对象无法析构。	高并发故障 FD泄漏 TooManyOpenFiles 稳定性 Chapter02
【Linux 运维调优】在部署高并发常驻服务（如 Workerman、Swoole、Nginx）前，为什么运维第一件事就是检查并调大 <code>ulimit -n</code>？	<b>1. 系统默认限制</b>：<br>大多数 Linux 发行版默认单进程允许打开的最大 FD 数量仅为 <b>1024</b>；<br><br><b>2. 并发致命瓶颈</b>：<br>在 Linux 网络编程中，每个接入的 TCP 连接都必须独占一个 FD。上限为 1024 意味着即便内存 CPU 极其富余，扣除系统自带文件后最多只能维持约 1020 个并发长连接！<br><br><b>3. 生产标准</b>：<br>上线前必须调高至 <code>ulimit -n 102400</code>（10万+）甚至百万级别，才能发挥高并发服务器的真正威力。	Linux调优 ulimit 高并发 TCP连接数 Chapter02
【Linux I/O 模型】执行 <code>fread(STDIN, 1024)</code> 读取 0 号键盘管子时，为什么代码会停滞卡住不动？什么是阻塞 I/O？	<b>1. 卡住原因</b>：<br>键盘管道当前没有数据输入，内核缓冲区为空；<br><br><b>2. 阻塞（Blocking I/O）本质</b>：<br>当请求的资源尚未就绪时，操作系统会让调用者进程<b>立刻交出 CPU 调度权并进入挂起睡眠等待状态</b>，直至硬件产生输入中断、数据写入缓冲区后才重新唤醒进程；<br><br><b>3. 局限性</b>：<br>阻塞期间进程无法响应任何其他任务，这就是为什么单进程处理海量连接必须走向多路复用（select/epoll）或非阻塞 I/O。	Linux网络 阻塞IO IO模型 STDIN Chapter02
【Linux 文件并发】当两个不同的 PHP 进程同时向同一个 <code>log.txt</code> 执行 <code>fwrite</code> 时，为什么内容会穿插错乱？如何解决？	<b>1. 错乱原因</b>：<br>多个进程各自持有独立的写偏移量，操作系统的时间片调度交错切换，发生<b>竞态条件（Race Condition）</b>；<br><br><b>2. 解决方案（文件锁）</b>：<br>使用 <code>flock($fp, LOCK_EX)</code>（排他互斥锁）。写入前加锁排队，写完后调用 <code>flock($fp, LOCK_UN)</code> 释放；<br><br><b>3. 高效替代</b>：<br>以追加模式 <code>fopen(..., 'a')</code> 打开（内核底层置位 <code>O_APPEND</code>），在小块写入（低于 Linux PIPE_BUF 4KB）时由内核在驱动层保证单次写入原子性。	Linux并发 flock 文件锁 竞态条件 原子写入 Chapter02
