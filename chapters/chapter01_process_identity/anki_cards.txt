【Linux 设计哲学】Linux 的 <code>/proc</code> 目录到底存放在哪块物理硬盘上？为什么被称为“海市蜃楼（伪文件系统 procfs）”？	<b>1. 存储位置</b>：<br><b>完全不在任何硬盘上！它只存在于内核内存中（procfs）</b>。<br><br><b>2. 设计哲学（一切皆文件）</b>：<br>为了让管理员无需专门编写一套专有调试 API，Linux 将内核中的进程控制块（PCB）、内存占用、打开的文件描述符等数据，动态投射为文件夹与文本文件。用最普通的 <code>cat</code> 和 <code>ls</code> 即可看穿进程内部；<br><br><b>3. 动态特性</b>：<br>进程存活时 <code>/proc/$PID/</code> 实时可见；进程一旦退出，该目录瞬间凭空蒸发。	Linux内核 procfs 伪文件系统 设计哲学 Chapter01
【Linux 进程探秘】<code>/proc/$PID/cmdline</code> 和 <code>/proc/$PID/status</code> 分别记录什么信息？<code>cli_set_process_title</code> 涂改的是哪一个？	• <b><code>/proc/$PID/cmdline</code></b>：记录进程启动时的完整命令行参数与自定义进程标题。<code>cli_set_process_title()</code> 改写的就是这里的内存内容，因此改变了 <code>ps aux</code> 最后一列的名字；<br><br>• <b><code>/proc/$PID/status</code></b>：以可读文本格式记录进程全套档案（如 <code>Name</code> 原始短名、<code>State</code> 运行状态 R/S、<code>VmRSS</code> 真实占用的物理内存、<code>Uid/Gid</code> 权限等）。	Linux命令 proc cmdline status 进程监控 Chapter01
【Linux 进程环境】为什么后台守护进程用相对路径 <code>fopen(&quot;./data.txt&quot;)</code> 时容易报错找不到文件？如何解决？	<b>1. 踩坑原因</b>：<br>每个进程都有一个“当前工作目录（cwd, Current Working Directory）”，可在 <code>/proc/$PID/cwd</code> 查到。常驻后台运行或系统服务启动时，cwd 可能被重设为根目录 <code>/</code> 或系统目录，导致相对路径断裂；<br><br><b>2. 规范解决方案</b>：<br>• 一律使用魔术常量拼接绝对路径：<code>__DIR__ . '/data.txt'</code>；<br>• 或在入口脚本显式锁定工作基准目录：<code>chdir(__DIR__);</code>	Linux进程环境 cwd chdir 相对路径陷阱 Chapter01
【Linux 安全机制】为什么监听 80/443 端口必须具有 <code>root</code> 权限？但为什么绝对不能长期以 <code>root</code> 身份运行 PHP 业务代码？	<b>1. 特权端口机制</b>：<br>Linux 规定 1~1023 号端口为特权保留端口，只有 UID=0（root）才有资格调用 <code>bind()</code> 监听，防止普通用户恶意截获系统核心服务流量；<br><br><b>2. 长期以 root 运行的致命危机</b>：<br>PHP 业务代码庞大，一旦存在文件上传漏洞、SQL 注入提权或任意命令执行（RCE），黑客便直接拥有 root 最高特权，可执行 <code>rm -rf /</code> 删库或完全接管整台服务器。	Linux安全 特权端口 权限隔离 Chapter01
【Linux 系统编程死穴】root 进程降权为平民（如 www-data, UID=33, GID=33）时，为什么必须<b>先调 <code>posix_setgid(33)</code>，最后再调 <code>posix_setuid(33)</code></b>？顺序反了会怎样？	<b>1. 铁律顺序</b>：<br><b>先改组（GID），最后改用户（UID）！</b><br><br><b>2. 致命陷阱</b>：<br>内核检查你是否有特权修改组别，看的是你当前的 <code>UID</code> 是否为 0（root 皇上）。<br><br><b>3. 颠倒顺序的后果</b>：<br>若先调用 <code>posix_setuid(33)</code>，你当场就变成了普通平民；下一行再试图执行 <code>posix_setgid(33)</code> 时，内核会以“平民无权修改组别”为由报错（Permission denied）！导致进程虽变成了平民用户，却依旧保留在 root 贵族组中，留下了重大安全后门！	Linux安全 权限降级 setuid setgid 生死陷阱 Chapter01
【Workerman 源码精读】在 <code>Worker::setUserAndGroup()</code> 中，大师是如何实现权限降级的？	Workerman 原版源码片段：<br><code>if (!posix_setgid($gid) || !posix_initgroups($userInfo['name'], $gid) || !posix_setuid($uid)) {<br>&nbsp;&nbsp;&nbsp;&nbsp;static::log(&quot;Warning: change gid or uid fail.&quot;);<br>}</code><br><br><b>逐行解析顺序</b>：<br>1. <code>posix_setgid($gid)</code>：先降主部门（主组）；<br>2. <code>posix_initgroups(...)</code>：降附加部门（附加组）；<br>3. <b>最后压轴调用</b> <code>posix_setuid($uid)</code>：彻底完成降权放弃皇上特权！	Workerman源码 setUserAndGroup 权限降级 Chapter01
【Linux 进程规范】子进程退出状态码（Exit Code）的取值范围是多少？0 与非 0 分别代表什么含义？在命令行如何读取上一个命令的退出码？	<b>1. 取值范围</b>：<br><b>0 ~ 255</b>（底层为一个无符号 8 位单字节数值）；<br><br><b>2. 含义规范</b>：<br>• <b><code>0</code></b>：成功，圆满执行完毕退出（Success）；<br>• <b>非 0（如 1, 250, 255）</b>：异常、错误中断，不同数字代表不同具体原因；<br><br><b>3. 命令行读取</b>：<br>• Linux Bash / WSL：<code>echo $?</code><br>• Windows PowerShell：<code>$LASTEXITCODE</code>	Linux基础 退出码 ExitCode 进程管理 Chapter01
【PHP 核心特性】当常驻进程因致命错误（Fatal Error）瞬间崩溃暴毙时，普通 try-catch 无法捕获，如何确保在咽气前记录下错误原因？	<b>1. 临终遗嘱函数</b>：<br><code>register_shutdown_function(callable $callback);</code><br><br><b>2. 错误死因提取</b>：<br>在回调中配合调用 <code>error_get_last()</code>，能抓取到导致进程崩溃的错误类型、错误信息、出错文件与行号；<br><br><b>3. 触发时机</b>：<br>无论是正常执行结束、代码中主动 <code>exit()</code>，还是遭遇致命错误 Fatal Error 暴毙，PHP 在彻底释放进程内存前必定执行该钩子函数！	PHP核心 register_shutdown_function 错误处理 Chapter01
【Workerman 源码精读】Workerman 子进程在启动时注册了 <code>register_shutdown_function(static::checkErrors(...))</code>，并在事件循环末尾写了 <code>exit(250)</code>。这套机制的作用是什么？	<b>1. 临终日志记录</b>：<br>在子进程崩溃的最后关头，<code>checkErrors()</code> 抓取 <code>error_get_last()</code> 并格式化写入主日志文件，避免毫无动静地死掉；<br><br><b>2. exit(250) 的妙用</b>：<br><b>250</b> 是 Workerman 约定的特殊退出状态码。Master 主进程通过 <code>pcntl_wait</code> 监听到子进程带着 250 死亡时，能准确识别出“这是非正常阵亡（非人为 stop/reload）”，立刻发出告警并重新 fork 补生一个新子进程，保障高可用！	Workerman源码 checkErrors exit250 高可用守护 Chapter01
【Unix 守护进程修养】为什么 Unix 守护进程规范（APUE）要求必须执行 <code>chdir('/')</code>？若不执行在生产环境中会引发什么挂载死锁？	<b>1. 根本原理</b>：<br>在 Linux 内核中，进程的 <code>task_struct-&gt;fs-&gt;pwd</code> 持有当前工作目录所在挂载点（<code>vfsmount</code>）的引用计数。只要常驻后台进程未退出，挂载点就始终处于“被占用”状态；<br><br><b>2. 生产惨案（EBUSY 死锁）</b>：<br>若守护进程在独立数据盘（如 <code>/data</code> 或 NFS/EBS 云盘）下启动，运维执行 <code>umount /data</code> 时，内核会拒绝并报错 <code>Device or resource busy</code>，导致磁盘无法热拔插、维护扩容受阻；<br><br><b>3. 根目录避风港</b>：<br>根分区 <code>/</code> 在系统运行期间永不卸载，将立足点迁至 <code>/</code> 可彻底解除挂载依赖。	Unix规范 守护进程 APUE chdir EBUSY Chapter01
【Workerman 架构权衡】为什么 Workerman 在 <code>Worker::daemonize()</code> 中没有按照 Unix 规范强行调用 <code>chdir('/')</code>？	<b>1. 调试与常驻一致性</b>：<br>PHP 业务代码中大量使用了相对路径（如 <code>require './config.php'</code>、读取相对路径证书等）。若 Workerman 开启 <code>-d</code> 守护模式时底层强行 <code>chdir('/')</code>，会导致原本在 Debug 模式运行正常的业务代码瞬间因找不到相对路径文件而 Fatal Error 崩溃；<br><br><b>2. 框架权衡原则</b>：<br>Workerman 选择保留用户启动脚本所在的立足点，转而通过内部全量锁定绝对路径的“防漂移架构”来保障框架自身的绝对稳定。	Workerman架构 daemonize chdir 路径兼容 Chapter01
【Workerman 源码精读】Workerman 如何通过 <code>debug_backtrace</code> 锚定世界坐标系原点？为什么不用 <code>$argv[0]</code>？	<b>1. 源码真迹</b>：<br><code>$backtrace = debug_backtrace(DEBUG_BACKTRACE_IGNORE_ARGS);<br>static::$startFile = static::$startFile ?: end($backtrace)['file'];<br>$startFileDir = dirname(static::$startFile);</code><br><br><b>2. 为什么不用 $argv[0]</b>：<br>若用户在其他目录下以相对路径运行（如 <code>cd /var/log &amp;&amp; php ../www/start.php</code>），<code>$argv[0]</code> 只是易碎的相对路径，cwd 改变立刻失效；<br><br><b>3. 机制透视</b>：<br><code>end($backtrace)['file']</code> 是 Zend 引擎启动最初入口文件时赋予的<b>物理绝对规范路径</b>，无论在哪个目录敲命令，都能精准锁定绝对基准目录 <code>$startFileDir</code>！	Workerman源码 debug_backtrace 防漂移 startFile Chapter01
【Workerman 源码精读】如果 Workerman 的 PID 文件使用相对路径，在运维管理时会引发什么致命事故？源码是如何防范的？	<b>1. 幽灵进程与端口冲突</b>：<br>若使用相对路径，运维在 <code>/root</code> 启动服务，PID 写入 <code>/root/workerman.pid</code>；部署脚本在 <code>/var/www/</code> 执行 <code>php start.php reload</code> 时找不到 PID 文件而报错 <code>not run</code>，误以为没启动又再次启动，导致两套进程争抢端口（<code>Address already in use</code>），老进程沦为无法通过命令停止的“幽灵孤儿进程”；<br><br><b>2. 源码防漂移闭环</b>：<br><code>static::$pidFile = static::$pidFile ?: sprintf('%s/workerman.%s.pid', $startFileDir, $startFilePrefix);</code><br>启动写入与 CLI 控制命令均通过绝对基准目录计算，保证读写永远命中同一个物理文件！	Workerman源码 pidFile 幽灵进程 防漂移 Chapter01
